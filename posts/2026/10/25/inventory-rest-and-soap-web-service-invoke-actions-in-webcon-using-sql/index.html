Inventory REST and SOAP Web Service Invoke Actions in WEBCON Using SQL

Oct 25, 2026 9 min read System Version: 2026.1.6.209

Learn how to inventory REST and SOAP invoke actions in WEBCON using SQL, including connections, automation hierarchy, methods, and request configuration.

Introduction

Integrations with external systems are often distributed across multiple WEBCON applications, processes, and automations. As the number of integrations grows, maintaining a clear overview of where REST and SOAP web services are invoked becomes increasingly challenging.

Whether you’re documenting existing integrations, troubleshooting connectivity issues, reviewing dependencies, or preparing updates and upgrades to WEBCON or connected systems, knowing which actions are configured and where they are used is essential.

This article provides a SQL query to inventory REST and SOAP invoke actions across your WEBCON environment, including their application and process context, automation hierarchy, connections, methods, and request configuration.

Prerequisites

You need read access to the WEBCON SQL database and a SQL client such as SQL Server Management Studio. The query uses tables described in the official WEBCON 2026 database documentation, including WFActions, Automations, WFDefinitions, WFApplications, WFApplicationsGroups and WFDataConnections.

What the query returns

InformationColumns
Scope and statusScope, ActionType, IsActive
REST settingsRESTHttpMethod, RESTRequestMode, RESTRequestSuffix
SOAP settingsSOAPWebServiceURI, SOAPWsdlURI, SOAPMethod
Application contextApplication group, application and process name, ID and GUID
Automation contextAutomationName, AutomationID, AutomationGUID, ActionPath
Action detailsActionName, ActionID, ActionGUID, ActionDescription
ConnectionConnectionName, ConnectionID, ConnectionGUID
Request configurationRequestBody

Each matching action appears as a row, including inactive actions. A missing value means the corresponding information was not resolved or extracted, not necessarily that the setting is unused.

SQL query

Disclaimer: This SQL query was created with the assistance of AI. Although it is intended for read-only use, always review and validate the query before executing it. It is recommended to use a test environment and ensure that a recent database backup is available.

Note: The query uses a recursive Common Table Expression (CTE) to resolve nested automation hierarchies and build the ActionPath. Due to this structure, it cannot be used directly in a WEBCON SQL data source and must be executed separately, for example in SQL Server Management Studio (SSMS).

Understanding the results

Action types and methods

ACT_ActionKindID identifies REST (78) and SOAP (32) Invoke actions. For REST, RESTHttpMethod maps the stored codes to GET, POST, PUT, PATCH, DELETE, GET_WITH_BODY and DELETE_WITH_BODY (codes 0 through 6, respectively). SOAP is a separate action type, not an HTTP method; its operation appears in SOAPMethod.

Automation hierarchy and scope

An Invoke action inside a ForEach operator may reference that nested operator rather than the top-level automation. The recursive query follows Automations.AUTM_AUTMID to the highest parent and builds ActionPath from the nested operator names, separated by >. The Invoke action itself remains in ActionName.

For example:

Scope is Process if a process can be resolved, Global if an automation but no process can be resolved, and Unassigned otherwise. These are reporting classifications. Global actions may therefore have empty application or process fields.

Connections and request settings

The query extracts a connection reference such as #WFC:5# from ACT_Configuration and resolves it through WFDataConnections. REST settings include the HTTP method and stored URL suffix; SOAP settings include service URI, WSDL URI and method.

RESTRequestMode is inferred: a non-empty stored SwaggerEndpoint means Swagger, otherwise Custom. This may not always reflect the current Designer Studio selection. RESTRequestSuffix is returned as stored, potentially including an HTTP method such as /groups GET.

RequestBody extracts content from <JsonCommunicate> for REST or the <parameters> XML fragment for SOAP. It does not cover all REST body formats or represent a complete SOAP envelope. Empty output does not prove that no payload is sent.

Filtering the Results

The query can be easily customized by adding conditions to the WHERE clause. For example, you can filter by:

  • Action type: REST or SOAP (ACT_ActionKindID)
  • Activity status: Active or inactive actions (ACT_IsActive)
  • Scope: Global or process-associated automations (Scope)
  • Application: Actions belonging to a specific application (APP_ID)
  • Connection: Actions using a particular data connection (WFC_ID)

These filters can also be combined to narrow down the inventory to specific integrations.

Using the inventory

Export the result to Excel or another reporting tool to identify affected Invoke actions before upgrading WEBCON, changing API endpoints, replacing connected systems or reviewing legacy integrations. Filter by connection, application, process, action type or activity status to narrow the review. Use AutomationName, ActionPath and ActionName to locate each configuration in Designer Studio.

Limitations

  • The query covers only these two Invoke action kinds, not integrations implemented through other actions, business rules, data sources or custom code.
  • Extraction relies on specific serialized tags in ACT_Configuration. Other formats or future WEBCON versions may require adjustments.
  • RESTRequestMode is heuristic, and RequestBody covers only the described configuration fragments.
  • The automation traversal uses MAXRECURSION 100; a cycle or excessive depth causes an error.
  • The result describes stored configuration, not endpoint availability, runtime values or execution history.

Conclusion

This inventory makes REST and SOAP dependencies easier to find before upgrades or changes to connected systems. It combines action details, connection references and nested automation locations in one read-only report, providing a practical starting point for impact analysis.
